# GitHub Pages and search setup

This is a static frontend application. Angular renders HTML during the build; visitors need no
application server or account. Upload only `dist/codemaster-academy/browser/`.

## Choose an address

Start with GitHub's free address: `https://YOURNAME.github.io/codemaster-academy/`. A short repository
name keeps lesson links readable. The supplied workflow discovers the final address automatically.
You can add a custom domain later. A brand name such as `codemasteracademy.dev` is an option if it is
available; availability has not been checked. A domain name alone does not improve search rankings.

For a custom domain, use GitHub Pages settings to configure the domain and the DNS records GitHub
shows. Enable HTTPS, then rerun the workflow. The workflow uses the configured domain for every
canonical link and sitemap entry. Do not keep old copies of the site at several unrelated domains.

This checkout already has Git history on the `master` branch and an `origin` remote set to
`https://github.com/AKSBhardwaj/codemaster-academy.git`. That local setting does not confirm that
the repository has been created on GitHub. If it already exists in your account, use it and skip
creating another repository.

In a terminal opened in this project folder, review and commit any remaining changes:

```powershell
git status
git add .
git commit -m "Prepare CodeMaster Academy for GitHub Pages"
```

If Git reports no changes, skip the commit. Then check the destination and upload the project:

```powershell
git remote -v
git push -u origin master
```

If you choose a different account or repository name, first update the existing remote with
`git remote set-url origin https://github.com/YOURNAME/YOUR-REPOSITORY.git`. For a fresh copy
without an `origin`, use `git remote add origin` with that address instead. Use your current branch
name when pushing; the supplied workflow runs automatically for both `main` and `master`.

For the currently configured account and repository, the expected free site address is
`https://AKSBhardwaj.github.io/codemaster-academy/`. The address becomes available after Pages is
enabled and the first deployment succeeds. You do not need a paid domain or a separate backend.

## Deploy from GitHub

1. Push these files and `package-lock.json` to your repository.
2. Open **Settings → Pages** and choose **GitHub Actions** as the source.
3. Open **Actions → Publish CodeMaster Academy → Run workflow**. Pushes to `main` and `master` also run it.
4. Wait for the build and deploy jobs. Open the URL shown by the deploy job.
5. Open a lesson directly, refresh it, run the SQL playground and try a narrow phone screen.

The workflow runs lint, tool type checks, deployment URL tests and application unit tests. It then
compiles all content, renders all routes, audits the final HTML and uploads only static files.
The build fails for incomplete topics, invalid metadata or missing sitemap pages.

`PUBLIC_SITE_URL` overrides automatic URL detection. Without it, a build in GitHub uses
`GITHUB_REPOSITORY`; outside GitHub it defaults to localhost. `src/content-schema/site-deployment.ts`
is generated by the build. Do not edit it to configure production.
Development commands (`npm start` and `npm run build:dev`) always use localhost and a root path,
even when deployment environment variables are present.

To make a public build locally in PowerShell:

```powershell
$env:PUBLIC_SITE_URL = 'https://YOURNAME.github.io/codemaster-academy/'
npm ci
npm run build:pages
```

Use your actual address in place of the example. To return to normal local development:

```powershell
Remove-Item Env:PUBLIC_SITE_URL -ErrorAction SilentlyContinue
npm start
```

`npm run build` and `npm run build:pages` run the same production pipeline. `CONTENT_ONLY` is for
content development and is rejected for a release. Do not upload `.generated`, Angular source,
`node_modules` or build-time server files. GitHub Actions handles the upload for you.

## Search engines

The site includes rendered lesson HTML, unique titles and descriptions, canonical links,
Open Graph and Twitter previews, a sitemap, robots directives, semantic headings and structured
data for lessons, courses and breadcrumbs. Personal learning pages and search results are marked
`noindex`. Unknown URLs use a real `404.html`; no rewrite sends every URL to the homepage.

After the site is public:

1. Add the exact public URL to [Google Search Console](https://search.google.com/search-console).
   For a custom domain, a DNS domain property covers the whole domain. For a GitHub project site,
   use a URL-prefix property and the verification method shown there. A verification HTML file can
   be placed in `public/` and published through the workflow.
2. Add the same site to [Bing Webmaster Tools](https://www.bing.com/webmasters/). You can import a
   verified Search Console site or follow Bing's verification instructions.
3. Submit the sitemap shown by the build, for example
   `https://YOURNAME.github.io/codemaster-academy/sitemap.xml`, in both services.
4. Inspect the homepage and a few lesson URLs. Check that crawlers receive the full lesson text,
   that the canonical uses the public address, and that the pages are eligible for indexing.
5. Use search reports to improve lessons that learners find confusing and to fix broken links.

Google and Bing decide whether and when to index or rank pages. Technical SEO makes the content
crawlable; it cannot guarantee a position or inclusion in every search engine. Verification and
sitemap submission need the published site and the owner's search-console account, so they have
not been performed by this project build.

The audit report is saved to `dist/codemaster-academy/seo-report.json`. Rerun `npm run seo:check`
against a completed build. The report lists route, sitemap and tutorial counts plus any failures.

## Check loading speed

Audit the production files that will be uploaded, using a fresh browser profile:

```powershell
npm run build
npm run preview
```

Open the printed preview URL (normally `http://localhost:4173/`) in Lighthouse. The preview
compresses text files like a static host, preserves repository prefixes, and returns real 404s.
`npm start` serves the development version with debugging code and unoptimized styles; its
performance score does not describe the published build. Keep the same device and throttling
settings when comparing results, and use several runs because timing varies with machine load.

The release inlines page styles and preserves both colour themes and the font before the full
stylesheet arrives. Search code loads when the learner opens search. No application server is
needed for these improvements.

## Machine-readable tutorial guides

Content builds generate `llms.txt` with links to the real lessons and static JSON reading files,
plus `.well-known/ard.json` describing the tutorial catalog. Every page advertises both files
with links that preserve the configured repository prefix. These guides do not expose account
data, create agent tools, or promise better search rankings.

Lighthouse 13.6 looks for `llms.txt` only at the domain root. A project site at `/repository/`
publishes its guide at `/repository/llms.txt`; a domain owner can also put that guide at
`/llms.txt` through their user Pages repository. The ARD audit follows the page's `rel="ard"`
link and supports project sites directly. Missing files should return 404, rather than the
homepage with a 200 response.
